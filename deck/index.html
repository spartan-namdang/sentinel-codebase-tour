Full note

Phần 1 nói về những quy ước chung của cả service. Mọi endpoint, mọi feature đều theo đúng những quy ước này, nên nắm được phần này là đọc được phần lớn codebase.

Bảy chủ đề: module, ba layer, đường đi của một request, cách tạo bean và config, phong cách API, cách xử lý lỗi, và cuối cùng là tám lỗi review hay trả về.

the shape of a service

Gradle multi-module. Small apps stay small, big services split by domain.

Small app, like Olympus


app/api-platform/       controllers, managers
app/module-client/      DTOs, Retrofit clients
app/module-postgresql/  repositories, sql/
app/module-exception/   SystemError
core/module-*/          database, SQS, email

One deployable app plus shared modules.

Big service, split by domain

Three modules per domain: api, repository, impl. Impls are wired runtimeOnly, so a domain can only see another domain's api.

Dàn ý

  • ⏱ 2,5 phút
  • Service = Gradle multi-module; mục lục là settings.gradle
  • Olympus là "small app": api-platform + 4 module app + core:*
  • Một feature thường chạm 4 module đầu
  • Service lớn: mỗi domain tách api / repository / impl
  • Animation: impl → api của domain khác thì compile; impl → impl thì không, vì runtimeOnly

Full note

Mọi backend của Spartan là một Gradle project nhiều module. Muốn biết service có những module nào thì mở settings.gradle, đọc nó như đọc mục lục.

Olympus thuộc dạng "small app". Có một module deploy được là app:api-platform, chứa controller, manager, factory, config và job. Bên cạnh là các module dùng chung: module-client chứa request/response DTO và Retrofit client, module-postgresql chứa table, entity, repository và toàn bộ file SQL migration, module-exception chứa SystemError là danh sách mọi mã lỗi API có thể trả về. Cuối cùng là các module core dùng chung như database, SQS, storage, email. Khi làm một feature, các bạn gần như chắc chắn sẽ chạm vào bốn module đầu.

Service lớn hơn thì tách theo domain, mỗi domain ba module: api chứa interface và model, repository, và impl. Điểm hay là impl được khai báo runtimeOnly. Nhìn animation: orders-impl phụ thuộc vào billing-api thì compile bình thường, nhưng nếu gọi thẳng vào billing-impl thì không compile được, vì impl không nằm trên compile classpath. Nghĩa là Gradle ép các domain chỉ nói chuyện với nhau qua api, không ai lách được.

three layers, no skips

Controller → Manager → Repository. Logic lives in one known place.

*Controller

Takes the request

Parses input, calls one manager, returns a response DTO. No business logic. No hand-written token or role checks.

*Manager

Owns the logic

Business rules, transactions, calls to repositories and services. Returns Either, never throws for expected failures.

*Repository

Talks to the database

Exposed DSL, one table family per repository. Every read filters deleted_at IS NULL.

*Service is a different thing: only for classes that talk to an outside system (email, S3, a vendor API) through Retrofit. If it has business rules in it, it's a Manager with the wrong name.

Dàn ý

  • ⏱ 2,5 phút
  • Ba layer, không được nhảy cóc: controller không gọi repository
  • Controller mỏng; quyền và role khai báo bằng @Secured, không tự viết tay
  • Manager giữ logic và transaction, trả Either
  • Repository: Exposed, luôn lọc deleted_at
  • Nói thêm (không có trên slide): kiểm tra "resource này có thuộc org của user không" nằm ở manager. Ví dụ DepartmentManager.update: so requesterOrganizationId với department.organizationId, khác thì trả USER_PERMISSION_INSUFFICIENT
  • Service ≠ Manager: Service chỉ để gọi ra ngoài

Full note

Đây là quy tắc quan trọng nhất của backend: request luôn đi Controller, rồi Manager, rồi Repository, không có đường tắt. Controller không bao giờ inject repository, kể cả chỉ để đọc một dòng.

Controller rất mỏng: đọc input, gọi đúng một manager, trả về response DTO. Không có business logic. Về quyền: role và đăng nhập được khai báo bằng annotation @Secured trên method, còn token thì filter của Micronaut xử lý. Controller không tự parse token hay tự viết if để kiểm tra role.

Có một câu hỏi các bạn sẽ gặp ngay: vậy kiểm tra "resource này có thuộc về tổ chức của user không" nằm ở đâu? Câu trả lời là ở manager. Controller lấy organizationId từ claims của token rồi truyền xuống. Manager đọc resource lên, so organization của resource với organization của người gọi, khác thì trả về lỗi USER_PERMISSION_INSUFFICIENT. Các bạn sẽ thấy đúng đoạn này trong DepartmentManager.update và delete lúc live demo. Có những endpoint nhận organizationId trong request body thì Olympus dùng thêm annotation @CheckOrganizationMatch để chặn sớm ở controller.

Manager là nơi duy nhất chứa business rule. Nó mở transaction, gọi repository, gọi service, và trả về Either: bên trái là lỗi, bên phải là kết quả. Lỗi dự đoán được thì không throw.

Repository chỉ nói chuyện với database bằng Exposed DSL. Mỗi repository lo một nhóm bảng, và mọi câu đọc đều lọc deleted_at IS NULL, vì Spartan soft delete chứ không xoá thật.

Cuối cùng, Service là một thứ khác hẳn: chỉ dùng cho class gọi ra hệ thống bên ngoài như email, S3 hay API của vendor. Nếu một class tên Service mà có business rule bên trong, thì thực chất nó là một Manager bị đặt sai tên.

the request path

One request goes down every layer and back.

  • In: JSON body becomes a request DTO, checked at the door
  • Down: controller → manager → repository → SQL
  • Up: entity becomes a response DTO, then JSON
  • Failure: .left() → getOrThrow() → one handler → { message, code }

Dàn ý

  • ⏱ 2 phút
  • Animation 1: request đi xuống đủ ba layer tới Postgres rồi quay lên
  • JSON → request DTO ở cửa vào; entity → response DTO ở cửa ra
  • Service (nét đứt) là nhánh phụ: manager gọi ra ngoài
  • Bấm next → animation 2: lỗi dự đoán được đi đường nào
  • Thread và connection pool để Part 2

Full note

Giờ ghép ba layer lại thành đường đi của một request. Nhìn chấm xanh: request đi từ client vào controller. Ở cửa vào, JSON được chuyển thành request DTO và được validate luôn. Controller gọi manager, manager gọi repository, repository chạy SQL xuống Postgres. Đường về thì ngược lại: repository trả entity, manager đổi entity thành response DTO, controller trả về, Micronaut serialize thành JSON với status 200.

Nhánh nét đứt phía dưới là Service. Khi manager cần gọi ra ngoài, ví dụ gửi email hay gọi API của vendor, nó gọi qua một Service. Đây là nhánh phụ, không phải một layer nằm giữa manager và repository.

(Bấm next.) Giờ là trường hợp lỗi dự đoán được, ví dụ không tìm thấy order. Manager không throw mà trả về .left() với mã lỗi. Controller gọi getOrThrow() ở cuối, lúc này mới throw ClientException. Exception đó được một handler duy nhất của cả app bắt lại và trả về JSON { message, code } với status lấy từ mã lỗi. Không ai tự build JSON lỗi bằng tay.

Ở đây mình cố tình chưa nói tới thread hay connection pool. Phần đó nằm ở Part 2.

wiring and config

Beans are built in factories. Numbers live in config.

@Factory builds plain classes


@Factory
class EmailFactory {
  @Singleton
  fun emailSender(config: EmailConfig) =
    when (config.provider) {
      "log" -> LogEmailSender()
      else -> SesEmailSender(config)
    }
}

No @Singleton on implementation classes. One file shows what is built; @Requires switches a bean on or off by config.

application.yml, not the code


app:
  email:
    provider: ${EMAIL_PROVIDER:log}
    timeout: ${EMAIL_TIMEOUT:5s}
    max-attempts: 3
  orders:
    list-limit-max: 200

Limits, timeouts, switches: a typed config class reads them. One place to look, one value per environment, no code change to tune.

Dàn ý

  • ⏱ 1,5 phút, nói lướt
  • Bean tạo trong class @Factory, không gắn @Singleton lên class implementation
  • Olympus: runtime/factory/ (ManagerFactory, RepositoryFactory…)
  • Ví dụ: gửi email. Local provider: log chỉ in email ra log; dev/prod đặt EMAIL_PROVIDER=ses
  • Olympus có đúng kiểu này: ExtractionFactory chọn fake hay OpenAI; ItviecFactory dùng @Requires(property = …)
  • Số, timeout, công tắc: nằm trong application.yml, ghi đè bằng env var

Full note

Ở Spartan, bean không được tạo bằng cách gắn @Singleton lên class implementation. Thay vào đó mỗi nhóm bean có một class @Factory, với từng method trả về một bean. Trong Olympus các factory nằm ở runtime/factory/: ManagerFactory, RepositoryFactory, ServiceFactory và vài cái khác. Lợi ích là mở một file là thấy được bean nào được tạo, từ dependency nào, và trong điều kiện nào. Ngoại lệ duy nhất là scheduler, vì Micronaut chỉ tìm @Scheduled trên bean thật.

Ví dụ trên slide là gửi email, thứ service nào cũng có. Factory đọc config provider: chạy local thì là log, email chỉ được in ra log chứ không gửi thật, nên các bạn không lỡ tay gửi mail cho ứng viên thật. Trên dev và prod, biến môi trường EMAIL_PROVIDER=ses chuyển sang gửi qua Amazon SES, với timeout lấy từ config. Code không đổi một dòng.

Olympus có đúng kiểu này ở hai factory thật. ExtractionFactory đọc config cv-extraction.provider: nếu là fake thì tạo extractor giả để chạy local và test, còn openai thì tạo client thật với timeout lấy từ config. ItviecFactory thì gắn @Requires(property = "app.itviec.enabled") ở cấp class: môi trường nào không bật thì cả nhóm bean không được tạo.

Bên phải là config. Nhà cung cấp email, giới hạn, timeout, công tắc bật tắt đều nằm trong application.yml, đọc qua một config class có kiểu, và mỗi giá trị có thể bị ghi đè bằng biến môi trường. Lợi ích: muốn biết timeout là bao nhiêu thì chỉ có một chỗ để tìm, mỗi môi trường đặt một giá trị riêng, và muốn chỉnh thì không phải sửa code.

the API style

RPC over HTTP. One style across every service.

RuleLooks likeWhy
GET only when the whole input fits in a query @Get("/detail") + ?id=… Read one thing by its id.
Lists are a POST, page in the body @Post("/list")
{ offset, limit, filter, sort }		 Filters and sort don't fit in a URL.
Every change is a POST with a verb @Post("/cancel"), /update, /delete No PUT, PATCH, DELETE. No path params.
Paths: /api/v1, plural, kebab-case @Controller("/api/v1/orders") Same shape for every entity.
snake_case on the wire, camelCase in code created_at ↔ createdAt
@QueryValue("order_id")		 Jackson converts bodies. Multi-word query params need an explicit name.

Dàn ý

  • ⏱ 3,5 phút
  • Chỉ hai verb: GET và POST. Chọn theo dạng input, không theo "đọc hay ghi"
  • GET: chỉ khi input nằm gọn trong query string, thường là đọc một thứ theo id
  • List là POST vì filter/sort/phân trang nằm trong body (PageableRequest)
  • Thay đổi: POST + động từ. Không PUT/PATCH/DELETE, không path param
  • Olympus: 17/23 controller dùng /api/v1/…; 6 controller cũ chưa có v1 (vd /api/department), code mới luôn dùng v1
  • snake_case trên wire; query param nhiều chữ phải đặt tên
  • Nguồn: apps/service/.claude/rules/backend-micronaut/API_DESIGN.md

Full note

API của Spartan theo kiểu RPC chạy trên HTTP, và mọi service dùng cùng một kiểu. Nguồn chính thức là file API_DESIGN.md trong .claude/rules của repo. Lưu ý: tài liệu HTTP API Design Guidelines cũ trên Notion đã lỗi thời ở vài điểm, cứ theo rule trong repo.

Chỉ có hai verb là GET và POST. Cách chọn không phải "đọc thì GET, ghi thì POST", mà là: GET chỉ dùng khi toàn bộ input nằm gọn trong query string, điển hình là đọc một thứ theo id, ví dụ /detail?id=….

Vì vậy list là POST. Một màn hình danh sách có filter, sort, search và phân trang, những thứ đó không nhét gọn vào URL được, nên đi trong body: offset, limit, filter, sort. Request DTO của list implement interface PageableRequest. Không dùng page/size.

Mọi thay đổi là POST kèm một động từ: /cancel, /update, /delete. Không có PUT, PATCH, DELETE, và không có path param kiểu /orders/{id}. Id luôn đi trong query hoặc body. Lợi ích: không ai phải tranh luận nên dùng verb nào.

Path bắt đầu bằng /api/v1, danh từ số nhiều, viết thường nối bằng gạch ngang. Trong Olympus có 6 controller cũ chưa có v1, ví dụ /api/department; các bạn sẽ thấy khi live demo, nhưng code mới thì luôn dùng /api/v1.

Trên wire là snake_case, trong Kotlin là camelCase, Jackson tự chuyển cho body. Riêng query param nhiều chữ thì phải đặt tên tường minh, ví dụ @QueryValue("vacancy_id") vacancyId, nếu không client gửi snake_case sẽ không khớp.

errors

Expected failures are values. Only surprises throw.

In the manager


override fun cancel(
  request: CancelOrderRequest
): Either<ClientException, OrderResponse> {
  val order = orderRepository.findFirst(id = request.id)
    ?: return SystemError.ORDER_NOT_FOUND.asException().left()
  if (order.status != OrderStatus.OPEN) {
    return SystemError.ORDER_NOT_OPEN.asException().left()
  }
  return transaction(db.primary) {
    val cancelled = orderRepository.cancel(id = order.id)
    orderEventRepository.insert(OrderEvent.cancelled(order))
    cancelled.toOrderResponse().right()
  }
}

In the controller


@Post("/cancel")
fun cancel(
  @Valid @Body request: CancelOrderRequest
): OrderResponse {
  return orderManager.cancel(request)
    .getOrThrow()
}

Not found, wrong state, not allowed: all .left(), returned early. The signature tells the caller what can go wrong.

One call at the end. getOrThrow() throws; one handler turns it into the HTTP response.

Two tables, one transaction(db.primary).

Dàn ý

  • ⏱ 3 phút
  • Manager trả Either<ClientException, T>; lỗi dự đoán được → return …left() sớm
  • Olympus viết kiểu early return .left() / .right(), không dùng either { raise }
  • Mã lỗi lấy từ enum SystemError (module-exception)
  • Hai bảng → một transaction(db.primary); đọc thì db.replica
  • Controller: một dòng getOrThrow() ở cuối
  • Nói thêm: kiểm tra org cũng là một .left() trong manager (xem DepartmentManager)

Full note

Quy ước xử lý lỗi: lỗi dự đoán được là giá trị, chỉ những thứ bất ngờ mới throw.

Bên trái là manager. Kiểu trả về là Either<ClientException, OrderResponse>. Đọc order lên, không có thì return sớm với SystemError.ORDER_NOT_FOUND.asException().left(). Order không ở trạng thái mở thì cũng return sớm một .left() khác. Không tìm thấy, sai trạng thái, không có quyền, tất cả đều là .left(). Chỉ cần đọc chữ ký hàm là biết hàm này có thể thất bại.

Trong Olympus các bạn sẽ thấy đúng kiểu viết early return này, với .left() và .right(). Một số service khác của Spartan dùng block either { } với raise, ý tưởng giống nhau, nhưng ở Olympus thì theo kiểu trên slide.

Mọi mã lỗi đều nằm trong enum SystemError ở module-exception: mỗi entry có HTTP status, mã số và message. Thêm lỗi mới là thêm một entry vào đó.

Một điểm nữa: cancel ghi vào hai bảng, đổi trạng thái order và thêm một event, nên cả hai nằm trong một transaction(db.primary). Hai bảng, hai lần ghi, một lần commit. Dữ liệu ghi dở dang là loại bug một tháng sau mới phát hiện. Ghi thì dùng db.primary, đọc thì db.replica; hiện chưa deploy replica nhưng vẫn phải chọn đúng pool.

Bên phải là controller: một dòng duy nhất ở cuối, .getOrThrow(). Nếu là .left() thì nó throw ClientException, và CustomExceptionHandler biến exception đó thành response HTTP. Không ai tự build JSON lỗi.

Nhắc lại ý ở slide ba layer: kiểm tra "order này có thuộc tổ chức của người gọi không" cũng chỉ là một .left() nữa trong manager. Mình bỏ khỏi slide cho gọn, các bạn sẽ thấy nó trong DepartmentManager.

what review will send back

Eight things every new engineer does here in the first month

!!

Force-unwrap. Use ?:, a null check, or requireNotNull.

layers

Logic in the controller, or a controller calling a repository.

N+1

A repository call inside map or forEach. Batch with listByIds, then associateBy.

txn

An email, queue or vendor call inside a transaction. Or two tables written without one.

counter

Read a count, add one, write it back. Two pods lose an update. Do the math in one UPDATE.

magic

A limit or timeout typed into code. It goes in config.

launch

GlobalScope, a fire-and-forget launch, runBlocking in a request. Do it now or hand it to a job.

mock

Mocking our own repository or manager. Real database; mock only outside systems.

Dàn ý

  • ⏱ 3 phút, mỗi mục ~20 giây
  • !!: Olympus hiện có 0 chỗ dùng trong code chính, giữ như vậy
  • N+1, counter, txn, launch: đều có rule trong PERFORMANCE.md và TRANSACTIONS.md
  • layers, magic: nhắc lại slide ba layer và slide config
  • mock: test đi qua HTTP thật và database thật (Part 2)
  • Chốt Part 1, chuyển sang Part 2

Đây là tám thứ mà gần như ai mới vào cũng bị review trả về trong tháng đầu. Biết trước thì đỡ được một vòng review.

Một, !!, force-unwrap. Dùng toán tử elvis, một câu if kiểm tra null, hoặc requireNotNull với message rõ ràng. Trong code chính của Olympus hiện không có chỗ nào dùng !!, hãy giữ như vậy.

Hai, layers: logic nằm trong controller, hoặc controller gọi thẳng repository.

Ba, N+1: gọi repository bên trong map hay forEach, 100 phần tử là 100 câu query. Hãy lấy hết id ra, gọi một lần listByIds, rồi associateBy để tra.

Bốn, txn: gọi email, queue hay API vendor bên trong transaction, connection bị giữ trong lúc chờ mạng. Hoặc ngược lại, ghi hai bảng mà không có transaction.

Năm, counter: đọc một số đếm lên, cộng một, ghi lại. Hai pod làm cùng lúc thì mất một lần cập nhật. Hãy để SQL tự cộng trong một câu UPDATE.

Sáu, magic: giới hạn hay timeout gõ thẳng vào code. Nó thuộc về config.

Bảy, launch: GlobalScope, launch rồi bỏ đó, hay runBlocking trong request. Việc gì thì làm ngay trong request, hoặc giao cho một job.

Tám, mock: mock repository hay manager của chính mình để test happy path. Test phải chạy với database thật; chỉ mock hệ thống bên ngoài.

DTOs

DTOs are the shape on the wire. They live in module-client.


@Introspected
data class CancelOrderRequest(
  val id: UUID,
  @field:NotBlank(message = "reason is required")
  @field:Size(max = 500)
  val reason: String,
  val notifyCustomer: Boolean = true
)

@Introspected
data class OrderResponse(
  val id: UUID,
  val status: OrderStatus,

{
  "id": "5f0c…",
  "reason": "Customer changed their mind",
  "notify_customer": true
}
  • @field: on every rule, never a bare @NotBlank
  • Non-null, no default: required
  • camelCase in Kotlin, snake_case on the wire
  • Bad input stops at the door: 400
  • Always one object back, never null

Dàn ý

  • ⏱ 3 phút
  • DTO nằm trong module-client/request và /response; không khai báo trong file controller
  • Validation: @field:NotBlank, @field:Size… (Olympus: 48 chỗ @field:NotBlank); message dạng "reason is required"
  • Non-null không default = bắt buộc; ? hoặc có default = tuỳ chọn
  • JSON bên phải: Jackson tự đổi notifyCustomer ↔ notify_customer
  • @Valid @Body ở controller → sai thì 400, manager không bao giờ thấy
  • Không có gì để trả thì SuccessResponse<Boolean>; list thì PaginationData

Full note

DTO là hình dạng của dữ liệu trên wire. Mọi request và response DTO đều nằm trong module-client, thư mục request và response. Rule của repo cấm khai báo data class ngay trong file controller, vì test và client Retrofit cũng dùng chung các DTO này.

Validation đặt trên field với tiền tố @field:, ví dụ @field:NotBlank, @field:Size, @field:Min. Đây là cách viết rule của Olympus yêu cầu; một @NotBlank trần trên constructor property của Kotlin có thể bị gắn vào tham số constructor thay vì field. Message theo mẫu "tên field is required".

Bắt buộc hay tuỳ chọn được thể hiện bằng kiểu: non-null mà không có giá trị mặc định là bắt buộc. Có dấu hỏi hoặc có default là tuỳ chọn. Ví dụ UpdateDepartmentRequest trong Olympus để name nullable, nghĩa là "không gửi thì giữ tên cũ".

Bên phải là JSON thật trên wire: notifyCustomer trong Kotlin trở thành notify_customer. Jackson tự chuyển, không cần annotation.

Controller nhận DTO bằng @Valid @Body. Input sai bị chặn ngay ở cửa với status 400, manager không bao giờ nhìn thấy request đó.

Response thì luôn là một object, không bao giờ null. Endpoint không có gì để trả như update hay delete thì trả SuccessResponse<Boolean>; list thì trả PaginationData.

the contract

The contract is code: a Retrofit interface next to the DTOs.


interface OrderClient {
  @POST("/api/v1/orders/cancel")
  suspend fun cancel(
    @Header("Authorization") token: String,
    @Body request: CancelOrderRequest
  ): Either<ErrorResponse, OrderResponse>
}
Renaming a field or adding a required one breaks every client already shipped. Change the contract on purpose.
  • Same DTOs as the controller: one definition
  • HTTP tests call the API through it
  • Rename a field and the tests stop compiling
  • Swagger is generated from the controller: the contract the web reads

Dàn ý

  • ⏱ 2 phút
  • Mỗi controller có một Retrofit client trong module-client (Olympus: DepartmentClient, VacancyClient…)
  • Dùng đúng DTO của controller, trả Either<ErrorResponse, T>
  • Test gọi API qua client này → đổi DTO là test hỏng lúc compile
  • Phía web: Swagger sinh từ controller là contract (slide sau)
  • Đổi contract là đổi có chủ đích: field đổi tên hoặc field bắt buộc mới phá client cũ

Full note

Contract của một endpoint không chỉ nằm trong tài liệu, nó là code. Với mỗi controller, module-client có một interface Retrofit mô tả đúng các endpoint đó: path, header, body và kiểu trả về. Trong Olympus các bạn sẽ thấy DepartmentClient, VacancyClient và nhiều client khác.

Client dùng chính các DTO mà controller dùng, nên chỉ có một định nghĩa duy nhất. Kiểu trả về là Either<ErrorResponse, OrderResponse>: lỗi HTTP nằm bên trái, kết quả nằm bên phải.

HTTP test gọi API qua client này. Hệ quả: nếu ai đó đổi tên một field trong DTO, test không compile được nữa, và lỗi được phát hiện trước khi lên review.

Phía web không dùng Retrofit. Web đọc Swagger, cũng được sinh ra từ controller. Slide sau nói tiếp.

Lưu ý ở callout: đổi contract phải có chủ đích. Đổi tên field, hoặc thêm một field bắt buộc, sẽ làm hỏng mọi client đang chạy, kể cả bản web đã deploy. Nếu buộc phải đổi thì thêm field mới dạng tuỳ chọn trước, hoặc hỏi lead.

the other side of the contract

The web never hand-writes an API call.

  • pnpm gen-api reads Swagger from a running backend
  • New endpoint? Add it to endpoints.allowlist.ts first
  • Types are camelCase; axios-case-converter handles the wire
  • Never edit __generated__/ by hand

Dàn ý

  • ⏱ 1,5 phút, chỉ giới thiệu, chi tiết ở buổi frontend
  • Controller → OpenAPI spec (Swagger) → pnpm gen-api (Orval) → hook + types → page
  • Olympus: hook nằm ở apps/web/src/__generated__/hooks/, vd useUpdateDepartment.ts
  • Endpoint mới phải được thêm vào src/__generated__/mutators/endpoints.allowlist.ts
  • Backend phải đang chạy khi gen

Full note

Đây là mặt bên kia của contract. Web không bao giờ tự viết lời gọi API bằng tay.

Micronaut sinh OpenAPI spec, tức Swagger, từ chính các controller. Bên web chạy pnpm gen-api; lệnh này dùng Orval đọc spec từ backend đang chạy, rồi sinh ra type và React Query hook, ví dụ useCancelOrder. Trang React chỉ việc gọi hook. Trong Olympus các hook nằm ở apps/web/src/__generated__/hooks/, ví dụ useUpdateDepartment.ts.

Hai lưu ý thực tế. Một, Orval trong Olympus chỉ giữ những endpoint có trong endpoints.allowlist.ts, nên thêm endpoint mới thì phải thêm vào đó trước, không thì chạy gen xong không thấy hook đâu. Hai, type phía web là camelCase; thư viện axios-case-converter đổi sang snake_case khi gửi đi và đổi ngược lại khi nhận về.

Và không sửa tay bất cứ file nào trong __generated__, lần gen sau sẽ ghi đè. Chi tiết về frontend có một buổi riêng.

error responses

One error shape. The status comes from SystemError.

  • Expected: manager returns .left(SystemError.X) → status and code from the enum
  • Bad input: @Valid fails before the controller runs → 400
  • Surprise: any other exception → 500, a generic message, an error log

Dàn ý

  • ⏱ 3 phút, bấm next 2 lần để đổi animation
  • Mọi lỗi cùng một khuôn { message, code }; code là số
  • 1. Lỗi dự đoán được: SystemError quyết định status, code, message (CustomExceptionHandler)
  • 2. Input sai: chặn trước controller, 400 (CustomErrorResponseProcessor)
  • 3. Bất ngờ: 500, message chung chung, log level error
  • Cảnh báo: đọc enum, đừng đoán status. Olympus DEPARTMENT_NOT_FOUND trả 400, không phải 404

Full note

Phía client chỉ thấy một khuôn lỗi duy nhất: JSON có message và code. code là một con số, ví dụ 2407 nghĩa là không đủ quyền. Web dựa vào code để hiển thị đúng thông báo. Có ba con đường dẫn tới response lỗi.

Một, lỗi dự đoán được, đang chạy trên màn hình. Manager trả .left() với một entry của SystemError, controller gọi getOrThrow(), và CustomExceptionHandler trả về status, code, message đúng như khai báo trong enum. Cả ba thứ nằm trên một dòng enum.

(Bấm next.) Hai, input sai. Request bị chặn ở @Valid, trước khi controller chạy. CustomErrorResponseProcessor gom các lỗi validation thành một message, status 400. Manager không bao giờ chạy.

(Bấm next.) Ba, bất ngờ: một NullPointerException, một lỗi SQL. Handler rơi vào nhánh còn lại: status 500, message chung chung, chi tiết được log ở level error chứ không trả ra ngoài. Nếu thấy 500 trong log thì đó là bug cần sửa, không phải một "lỗi nghiệp vụ".

Một cái bẫy có thật trong Olympus: status không phải lúc nào cũng như các bạn đoán. Ví dụ DEPARTMENT_NOT_FOUND được khai báo với status 400 chứ không phải 404. Khi viết test hay xử lý lỗi ở web, hãy mở SystemError ra đọc chứ đừng đoán.

threads and blocking

Six hops. Each one has a limit; past it, requests wait.

Block the event loop (02) and every request on the pod slows down. That's why every controller carries @ExecuteOn(TaskExecutors.IO).
Hold a connection (05) while calling an outside API and the pool drains. That's why no outside call runs inside a transaction.

Dàn ý

  • ⏱ 3 phút
  • Sáu chặng, mỗi chặng có giới hạn; quá giới hạn thì request phải chờ (chấm cam)
  • 02 Event loop: vài thread Netty phục vụ mọi connection, tuyệt đối không block
  • 03 IO pool: Olympus cố định 32 thread (executors.io.type: fixed). Mặc định Micronaut không giới hạn; Olympus cố định vì 128 thread tranh 20 connection thì 108 thread đứng chờ
  • 04 Code của mình chạy trên thread IO; JDBC là blocking nên mọi controller có @ExecuteOn
  • 05 Hikari: 10 connection cho primary (+10 replica)
  • Hai callout = hai lỗi kinh điển

Full note

Giờ nhìn cùng một request nhưng ở mức thread. Nó đi qua sáu chặng, và mỗi chặng có giới hạn. Quá giới hạn thì request phải xếp hàng chờ, chính là các chấm màu cam trong animation.

Một, socket: load balancer và TLS. Hai, event loop: một vài thread Netty phục vụ toàn bộ connection của pod. Thread này không bao giờ được phép block.

Ba, IO pool. Annotation @ExecuteOn(TaskExecutors.IO) chuyển handler từ event loop sang pool này. Trong Olympus pool được cố định 32 thread, khai báo trong application.yml. Comment trong file đó giải thích lý do: Micronaut mặc định không giới hạn pool, từng có lúc 128 thread cùng tranh 20 database connection, và 108 thread chỉ đứng chờ. Mình chỉ cần nhớ: pool đầy thì request mới phải chờ.

Bốn, code của mình: controller, manager, repository, tất cả chạy trên thread IO đó. Vì JDBC là blocking, nên cả 23 controller của Olympus đều có @ExecuteOn, kể cả những handler không phải suspend.

Năm, Hikari: pool database connection, 10 connection cho primary và 10 cho replica. Hết connection thì phải chờ, chờ lâu quá thì timeout. Sáu, Postgres: mỗi connection là một process phía server.

Hai callout bên dưới là hai lỗi kinh điển. Block event loop thì cả pod chậm theo. Giữ connection trong lúc gọi API bên ngoài thì 10 connection cạn rất nhanh, và mọi request khác phải đứng chờ ở chặng 05.

threads and blocking

Hold a connection only for SQL. Anything slow goes outside.

Vendor call inside the transaction


return transaction(db.primary) {
  val done = orderRepository.cancel(id = order.id)
  // HTTP call, up to 3 s, connection held
  carrierService.cancelPickup(order.id)
  done.toOrderResponse().right()
}

Commit first, hand the call to a job


val done = transaction(db.primary) {
  orderRepository.cancel(id = order.id).also {
    jobRepository.insert(CancelPickupJob(order.id))
  }
}
// a worker calls the carrier later
return done.toOrderResponse().right()
  • No runBlocking, no Thread.sleep in a request
  • Fire-and-forget? Hand it to a job, never GlobalScope
  • Every outside call has a timeout, and it comes from config

Dàn ý

  • ⏱ 2 phút
  • Trái: gọi vendor trong transaction → giữ connection 3 giây
  • Phải: commit nhanh, ghi một job; worker gọi vendor sau
  • Olympus làm đúng vậy: email đi qua outbox (email_deliveries), việc nền đi qua SQS
  • Ba quy tắc: không runBlocking/sleep, không GlobalScope, timeout lấy từ config

Full note

Từ slide sáu chặng rút ra một quy tắc: chỉ giữ connection cho SQL, những thứ chậm thì đưa ra ngoài.

Bên trái là lỗi hay gặp. Huỷ order xong thì gọi luôn API của hãng vận chuyển, nhưng lại gọi bên trong transaction. Cuộc gọi đó có thể mất tới 3 giây, và suốt 3 giây đó connection bị giữ. Mười request như vậy cùng lúc là pool cạn.

Bên phải là cách đúng. Transaction chỉ làm hai việc nhanh: đổi trạng thái order và ghi một job vào bảng, rồi commit. Một worker chạy nền sẽ đọc job và gọi hãng vận chuyển sau, ngoài mọi transaction, có retry. Olympus làm đúng kiểu này: mọi email ứng viên là một dòng trong bảng email_deliveries rồi scheduler gửi đi, còn các việc như trích xuất CV thì đi qua hàng đợi SQS.

Ba quy tắc ở dưới. Không runBlocking, không Thread.sleep trong request. Việc kiểu "bắn rồi quên" thì giao cho job, không dùng GlobalScope, vì lỗi ở đó sẽ biến mất không dấu vết. Và mọi lời gọi ra ngoài đều phải có timeout, giá trị lấy từ config.

the database shape

Every table looks the same. Business rules stay in the app.


-- sql/042-orders.sql
CREATE TABLE IF NOT EXISTS orders (
  id              uuid PRIMARY KEY
                  DEFAULT uuid_generate_v4(),
  organization_id uuid NOT NULL,
  status          text NOT NULL,
  created_at      timestamptz NOT NULL DEFAULT NOW(),
  updated_at      timestamptz,
  deleted_at      timestamptz
);
CREATE INDEX index_orders_by_organization_id
  ON orders (organization_id)
  WHERE deleted_at IS NULL;
CREATE TRIGGER trigger_orders_updated_at
  BEFORE UPDATE ON orders FOR EACH ROW
  EXECUTE PROCEDURE update_updated_at();

UUID, text, timestamptz, soft delete

Same shape in every table, so every repository reads the same way.

Rules live in the manager

No foreign keys, no CASCADE, no Postgres enums. The database keeps keys, NOT NULL, uniqueness, and the updated_at trigger.

A shipped migration is never edited

Flyway, numbered files. Wrong? Add a new one.

Dàn ý

  • Rule: .claude/rules/database/SCHEMA.md
  • Tên file migration Olympus: NNN-name.sql (vd 005-departments.sql), Flyway với prefix rỗng, separator -
  • uuid uuid_generate_v4(), text, timestamptz, deleted_at
  • Không FK, không CASCADE, không enum Postgres; có trigger updated_at
  • Unique index phải kèm WHERE deleted_at IS NULL
  • Migration đã merge thì không sửa; outOfOrder đang bật, trùng số vẫn fail

Full note

Mọi bảng trong Olympus có cùng một hình dạng: khoá chính uuid sinh bằng uuid_generate_v4(), chuỗi dùng text chứ không dùng varchar, thời gian dùng timestamptz, và ba cột chuẩn created_at, updated_at, deleted_at. Vì bảng nào cũng giống nhau nên repository nào đọc cũng giống nhau.

Quan hệ và business rule nằm ở app. Không có foreign key, không CASCADE, không enum của Postgres. Database chỉ giữ những gì nó làm tốt: khoá, NOT NULL, unique, và một trigger tự cập nhật updated_at mà bảng nào cũng có.

Một chi tiết hay bị quên: unique index phải kèm WHERE deleted_at IS NULL. Nếu không, một department đã xoá mềm vẫn giữ cái tên đó mãi mãi và không ai tạo lại được. Xem 005-departments.sql.

Migration chạy bằng Flyway, file đặt tên theo số thứ tự rồi gạch ngang, ví dụ 005-departments.sql. File đã merge thì không bao giờ sửa; sai thì thêm file mới. Olympus bật outOfOrder, nên file số nhỏ merge sau vẫn chạy, nhưng hai file trùng số thì vẫn lỗi.

the edges of the service

Auth comes in through filters. The outside world sits behind Retrofit.

coming in

JWT, then roles

Keycloak sign-in, then our own JWT carrying the organization. @Secured roles on each endpoint. The organization comes from the token, never from the URL.

going out

Retrofit, in a Service

Outside HTTP APIs through Retrofit, built in a factory with a timeout from config. A manager calls the service, never inside a transaction.

writing twice

One transaction

More than one table: one transaction(db.primary) around all of it, in the manager. Two writes, one commit.

Dàn ý

  • Vào: đăng nhập Keycloak (Google) → API phát JWT riêng có organization_id
  • @Secured(SecurityRole.…) trên method; controller đọc org bằng authentication.getCustomClaims()
  • Ra: Retrofit client tạo trong factory, timeout từ config, nằm trong *Service
  • Ghi nhiều bảng: một transaction(db.primary) trong manager
  • Chi tiết auth: session 4

Full note

Chiều vào: người dùng đăng nhập qua Keycloak bằng tài khoản Google, sau đó API kiểm tra và phát JWT của riêng Olympus, trong đó có organization_id. Mỗi endpoint khai báo role bằng @Secured. Controller lấy organization từ claims của token qua authentication.getCustomClaims(), không bao giờ lấy từ URL. Web dùng subdomain chỉ để định tuyến giao diện.

Chiều ra: gọi API bên ngoài bằng Retrofit interface, được tạo trong một factory với timeout lấy từ config. Client đó nằm trong một class Service. Manager gọi service, và không bao giờ gọi bên trong transaction.

Ghi vào nhiều hơn một bảng thì bọc tất cả trong một transaction(db.primary) ở manager. Hai lần ghi, một lần commit.

Phần auth chi tiết có session riêng, session thứ tư.
